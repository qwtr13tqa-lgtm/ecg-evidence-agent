# ECG证据查询Agent：架构、工程取舍与评测

[返回项目首页](Readme.md) · [使用说明](docs/user_guide.md)

## 定位

Agent是自然语言驱动的证据复核入口，不直接识别原始ECG，不自主训练SGRF-Net。波形看图优先交给界面，确定性计算交给代码；模型负责理解问题、选择工具和组织回复。

“指定一个窗口”可用参数解析和固定流程完成，不能仅凭此证明自主规划必要。批次筛选同样保留固定页面作为基线。

## 三条执行路径

| 路径 | 输入与执行 | 返回 |
|---|---|---|
| 产品帮助 | 常见功能问法匹配本地user_guide主题 | 确定性说明，无网关调用 |
| 当前分析 | 当前analysis_id摘要＋近期上下文→LLM工具调用→本地工具→继续查询或提交 | 经部分结构/数值/对象校验的草稿 |
| 所选批次 | 明确选择报告→一次LLM工具选择→本地逐条匹配历史 | 程序汇总状态及可打开的分析 |

这三条路径共用界面，不代表一个无限制的跨记录Agent。批次路径当前不读取完整旧对话以解析任意指代，也不支持任意窗口/RR跨样本计算。用户应明确选择本轮范围。

## 单条Agent运行机制

`ECGEvidenceAgent`用LangGraph组织decide/tools节点；`ToolGateway`适配原生Function Calling。模型输出调用请求，执行器校验参数并读取绑定分析的统计。工具结果包括证据ID和可引用字段路径，提交时检查引用和数值。

默认最多4次模型请求、6次工具调用；提交也计入工具预算。SDK重试关闭，重复相同工具参数被限制。非标量observation允许一次受预算约束的修正；真实错误数值不因此放行。未采用独立Planner；不要把所有纠错称为通用反思能力。

深度模型在本地分析时执行，之后窗口与RR工具主要查询保存结果，不每轮重跑模型。

## 记忆与范围

近期最多三轮成功问答用于理解追问，历史文字属于未验证上下文，不是本轮数值证据。历史工具对象按分析ID和轮次恢复；窗口含导联、起止点和来源。明确旧窗口后重新查询当前证据，多候选对象需澄清。

六轮案例验证过第一轮V2 [4200,4800)的恢复；这不等于支持任意自然语言指代或长期个人健康档案。

单条工具不因批次功能而解除绑定。批次结果明确记录报告哈希和source_analysis_id；外层证据ID以当前会话分析ID开头以符合历史保存契约，scope区分批次证据。不能将其他记录的摘要作为当前样本事实。

## 历史与可视化

`AnalysisStore`是运行时内存存储；`HistoryRepository`将分析和对话保存到SQLite，支持刷新/重启恢复。旧README所说“重启丢失会话”不适用于当前持久化网站。

“查看波形”由程序从成功引用的工具证据读取导联、起止点后绘图，不是LLM直接操纵任意界面。导出、删除、历史恢复不应默认依赖外部网关。

兼容历史检查涉及输入哈希、权重、适配器、裁剪、阈值、预测及分数；缺少版本证明的旧历史不擅自判为匹配。configured仅说明阈值配置，不代表该匹配通过。哈希和analysis_id约束不等于多用户鉴权。

## RAG

工程说明与ECG背景语料通过BM25检索，保存来源；早期语料为7条、开发查询8条。没有使用向量数据库，也没有证明可覆盖广泛医疗问题。检索命中不保证回答语义正确。

产品功能说明使用`docs/user_guide.md`，与医学背景语料分开。样本数值必须查工具，不能引用产品文档生成。

## 实际排障案例

| 现象 | 原因/定位 | 改动与验证范围 |
|---|---|---|
| 第六轮查成V1 [4730,4800) | 最近三轮丢失第一轮V2对象 | 结构化恢复＋重查＋对象校验；六轮回归通过 |
| 引用temporal_regions提交失败 | observations要求标量而模型提交列表 | 区分非标量错误，一次有预算修正；保留真实值检查 |
| 网站与test2分数不同 | 同输入同权重对照定位归一化差异 | 网站路径评测复用适配器；训练一致性仍待确认 |
| 524和180秒超时 | 请求日志支持网关/上游链路排查 | 不据此放宽数值校验；具体远端根因需服务日志 |
| 批次回答保存ValueError | 证据ID前缀和终态不符合历史契约 | 修正批次输出，不放宽历史隔离 |
| Windows临时文件测试失败 | 未关闭NamedTemporaryFile被再次打开 | 改用目录内写完关闭的文件验证哈希拒绝 |

## 评测结果怎么讲

- RR单例：固定工具和Agent都完成必要事实查询。案例中查询数分别为5和2，但Agent多模型往返、更慢。不同方案计数口径（尤其bootstrap和submit）需要说明。
- 窗口单例：两方案均完成。
- 缺失QTc案例：固定工具正确说明缺失，Agent曾因超时没有答案，应计交付失败。
- 六轮记忆：修复前对象错误，修复后恢复V2并引用本轮证据。
- 批次筛选：100条报告对应3条误报、16条漏报；自然语言查询曾耗时36.11秒，未证明比固定控件更方便。
- 补丁离线测试验证软件约束，不是Agent任务成功率或真实用户效率实验。

早期比较记录：批次146b0e7b-0f29-4a35-9bf0-f2c71e704d5f与e653bedc-a9f9-4858-9b53-156e5c10b132分别记录RR四方案4/4草稿完成、另三任务7/12草稿完成（5次超时）。这是旧文档保留的历史统计，未在本次重新核算，不与后续能力批次混加。

统一评分曾出现UNKNOWN元数据分组，不能将该汇总当作已完成的正式排行榜。评测应保留批次、模型、代码、输入、工具预算与人工评审状态。

推荐指标：完整任务成功率、对象正确率、数值/引用支持、失败率、端到端中位数与P95、模型调用/费用及人工操作次数。结构通过不替代人工语义评审。公平比较共用工具和数据，固定流程不能被故意限制为过弱基线。

## 环境与部署边界

早期环境记录为Linux、Python3.10.12、RTX3090及PyTorch2.6.0；后续用户实测Windows、Python3.10、PyTorch2.6.0+cpu、NumPy2.2.6。它们是不同机器/阶段的观测，不是完整支持矩阵。

网关通过ECG_API_KEY、ECG_BASE_URL、ECG_MODEL配置。超时日志只反映可观察阶段，不等于模型内部思考或精确远端排队时间。当前原型缺少多租户鉴权、生产级任务队列和服务保障；上线前还需数据授权、隔离、审计和独立性能评估。

## 面试概括

“我围绕自研ECG模型实现了受约束的证据查询层，重点处理工具执行、对象恢复、引用校验与波形复核。实际定位过跨轮对象错配、结构化提交错误、预处理差异和历史保存契约问题。简单任务保留固定入口，Agent的整体效率收益仍通过任务对照验证，不以框架数量或工具次数代替效果。”
