# ECG 证据复核 Agent：演示与失败案例

目的：用约 8–10 分钟讲清楚用户任务、执行方式、证据约束及工程取舍。底层模型仅作为专业分析器介绍，主讲 Agent。

## 开场（30 秒）

我做的是面向 ECG 模型研发人员的证据复核 Agent。模型与信号工具负责计算，LLM 负责理解问题、编排查询和解释证据。简单请求保留固定路径，集合任务使用结构化计划和本地执行，探索任务进入有预算的工具循环。重点是让每次操作可核对，并在错误或超时时保留证据与执行状态。

## 演示前准备

- 启动 `app_ecg.py`，使用已有分析与已匹配历史的批次。
- 先确认实际模型配置、数据和阈值版本，避免临场切换数据造成索引错配。
- 有网关授权才演示在线问答；准备同版本保存的成功及失败记录作为网络故障时的替代。
- 展示历史结果时明确说“这是保存的运行记录”，不要当作本次实时执行。
- 候选时间区域为空不是演示失败；它与手动指定窗口查询是两种对象。

## 演示一：一句话查询，并定位同一窗口（约 2 分钟）

**用户任务**：减少手动填写导联和采样坐标的操作。

1. 打开一条 500 Hz、4800 点的已完成分析，展示输入与重构叠加。
2. 提问：“查看 V2 最后 1.2 秒，给出起止采样点、均值和最大值。”
3. 核对请求对象为 V2、输入片段坐标 `[4200,4800)`，对应 `[8.4,9.6)` 秒。
4. 打开回答对应的波形入口，确认高亮与证据坐标一致。
5. 展开一条工具记录，说明 evidence_id、字段路径和数值如何关联。

**讲解重点**：均值与最大值来自保存的模型误差图，不是 LLM 计算；坐标换回原记录需要加裁剪起点。不要提前背诵另一条样本的均值。

**诚实边界**：该任务单轮解析加固定工具也能完成，不能用它证明 Agent 优势。

## 演示二：根据中间结果确定下一步参数（约 2–3 分钟）

**用户任务**：“找出最长的保留 RR 间隔，给出左右峰坐标；查询 V1 在这两个峰之间的模型分数均值和最大值。”

1. 查看 RR 工具返回的保留间隔与峰坐标。
2. 查看后续窗口查询，确认导联为 V1，起止点来自选中 RR 的两个峰。
3. 核对最终回答同时引用 RR 与窗口证据。
4. 如出现同长间隔，说明实际选择策略，不声称存在唯一最长值。

**讲解重点**：后一个工具的参数依赖前一个工具的真实返回结果。Agent 可以组合现有工具，不需要让 LLM 编写任意 Python 或直接访问文件。

**诚实边界**：固定工作流也可实现这条链。这里展示动态组合能力，不宣称规则方法做不到；实际是否更好仍需受控对照。

若工具结果缺少可用 RR，正确行为是说明无法确定窗口，不臆造坐标。

## 演示三：批次集合查询与失败恢复（约 3 分钟）

**用户任务**：“找出所有漏报中异常分数最低的 5 条记录。”

1. 选择一个有标签与预测的报告，展示批次范围与类别计数。
2. 核对实际计划：category=fn、score 升序、limit=5；同分按已实现的稳定策略核对。
3. 展示本地计算结果及匹配记录入口。没有匹配历史时应显示需要本地分析，不能假装读过波形。
4. 如时间允许，打开已保存的条件查询案例：先统计对照组某指标，再将统计值绑定给下一步筛选。
5. 展示 v3 中一次规划超时和一次预算内恢复的 trace，以及首次/最终通过指标。

**讲解重点**：LLM 解析条件，本地程序筛选、排序和统计。Top5 本身不需要逐条查询波形；复杂共性复核才按证据需要补查。

**诚实边界**：排序表不是漏报原因分析。FN 分数低于阈值是分类机制，不能直接解释病理或模型失效的因果原因。共性需要对照组、有效样本数、缺失与反例。

## 三个失败案例：问题 → 定位 → 修复 → 证据

### 1. 跨轮窗口指代恢复错误

- **现象**：只保留最近三轮对话时，第六轮无法可靠恢复第一轮窗口，可能查询到其他导联或区域。
- **定位**：对照用户要求、保存的窗口对象和本轮工具参数，而不是只看回答是否通顺。
- **修复**：按分析 ID 和轮次保存结构化窗口对象，恢复后重新查询；多候选需澄清，并限制跨分析引用。
- **证据**：已有六轮案例恢复第一轮 V2 `[4200,4800)`，并引用本轮重新查询的证据；另有窗口记忆边界测试。
- **边界**：不等于支持任意长期记忆、任意语言指代或个人健康档案。

### 2. 条件筛选使用数字占位，结果看起来合法却不正确

- **现象**：用户要求基于前一步统计结果筛选，计划却使用 0 作为阈值；空结果可能掩盖错误。
- **定位**：检查“参数从哪里来”，不能只检查类型、范围和最终 JSON。
- **修复**：通过 from_step/path 显式绑定依赖；阻止尚未计算时填入字面数字；上游没有有效值时停止后续筛选并说明不足。
- **证据**：边界集中加入真实非空结果和无有效对照值的案例，检查绑定与实际结果；v3 边界最终自动验收 7/7、字段 15/15。
- **边界**：7/7 是整个小型边界集结果，不能归功于单项修复，也不证明任意自然语言条件均被正确解析。

### 3. 规划超时让简单集合查询无法交付

- **现象**：明确缺失查询也进入规划器并超时；复杂请求还可能因多轮等待增加延迟。
- **定位**：分开记录规划、工具、提交及恢复阶段。90 秒客户端超时不能单独证明远端排队或模型思考的具体原因。
- **修复**：完整匹配的明确缺失条件走保守本地路径，含额外条件则回规划器；其他规划超时最多一次同输入、预算内恢复，计入请求与耗时。
- **证据**：v3 真实题首次 12/14，两个规划超时恢复后最终 14/14；共 12 次模型请求，总耗时约 379.88 秒。边界 7/7，明确缺失题零模型请求。
- **代价**：恢复提高交付机会，但真实题总耗时高于 v2；最终通过不是零超时，更不是速度全面提升。

## 常见追问

**为什么不直接看图？** 看图更适合直观判断，系统保留它。自然语言的作用是把参数查询、跨轮操作和集合筛选连接起来；是否更方便需要用户实验，不用模型调用次数替代效率。

**为什么不全部用规则？** 已覆盖的固定任务规则表现更好。临时工具组合可交给模型生成计划，但仍通过本地执行器和校验器约束；规则没有覆盖某问法不代表规则方法无法实现。

**用了什么 Agent？** 混合系统：规则快速路径、集合 Plan-and-Execute，以及受限 ReAct 式工具循环。不是每个问题都自主循环。

**最重要的工程贡献？** 将问题、执行参数、证据和回答连接起来，同时保留预算、范围与失败记录；通过真实坏例定位问题并量化修复代价。
